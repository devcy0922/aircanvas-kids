# 플랫폼 확장 계획 — 포털 + 게임 + 엄빠(서울형 키즈카페)

> **상태: 단계 0~4 구현(v0.8.0), 단계 5(정리)는 미착수.** 2026-10-21 사용자 결정("그대로 가")에 따라 구조·URL은 §4 제안대로 확정되었다(경로 방식, 게임은 `/play/`).
> 현재 동작은 `README.md`·`docs/architecture.md` §9가 기준이며, 이 문서는 결정·이행 기록과 서비스 추가 절차(§8)를 담는다.

## 1. 결정된 것 (사용자 지시)

- `kids`는 앞으로 **어린이·육아 관련 여러 콘텐츠를 담는 제품**이다. 지금까지 만든 공중 색칠 게임은 그중 **게임** 기능이다.
- **메인 페이지를 별도로 새로 만들고**, 게임은 그 아래 하위 페이지(기능) 하나로 둔다.
- 이전에 만든 **서울형 키즈카페 "엄빠"**(`/srv/products/s-kids`)를 새 하위 페이지로 붙인다.
- 저장소는 **모노레포**로 가는 방향을 검토한다(권고는 §2).

## 2. 모노레포 권고

**권고: 예. 다만 한 번에 합치지 않고 §5의 순서로 단계적으로 합친다.**

| 관점 | 판단 |
| --- | --- |
| 이미 npm workspaces(`apps/*`, `packages/*`)다 | 새 앱은 `apps/` 아래에 추가만 하면 된다. 구조 전환 비용이 작다. |
| 메인 페이지가 두 하위 서비스를 연결한다 | 링크·공용 디자인 토큰·공통 셸을 한 저장소에서 같이 바꿔야 어긋나지 않는다. |
| 혼자(사람+에이전트) 운영한다 | 저장소·체크리스트·배포 절차를 하나로 유지하는 쪽이 부담이 적다. |
| 스택이 다르다 | 게임은 Vite/React + Rust 릴레이, 엄빠는 의존성 없는 Node 서버 + 단일 HTML이다. **코드를 섞지 않고 앱 단위로 격리**하면 문제없다. |
| 법적·운영 성격이 다르다 | 엄빠는 외부 공공데이터·예약 사이트 호출 정책(`s-kids/docs/LEGAL_AND_ROBOTS.md`)이 있다. 문서·검증을 `apps/cafe` 안에 두고 게임 규칙과 섞지 않는다. |

**합치지 않는 편이 나은 경우**(현재는 해당 없음): 팀이 분리되거나, 엄빠가 별도 도메인·별도 일정으로 독립 출시될 때.

## 3. 목표 구조

```text
aircanvas-kids/                 (저장소 이름은 유지. 변경은 별도 결정)
├── apps/
│   ├── portal/   신규  kids 메인(런처). 정적 SPA, 서버 없음
│   ├── phone/    기존  게임: 폰 앱 (이름·경로는 당분간 유지)
│   ├── tv/       기존  게임: TV 앱
│   └── cafe/     이관  엄빠: s-kids의 demo/ (Node 서버 + 정적 파일 + data)
├── packages/
│   ├── protocol/ tv-art/   게임 전용 — 다른 앱이 import하지 않는다
│   └── ui/       신규(필요해지면)  포털·엄빠가 함께 쓰는 디자인 토큰·셸
├── server/       게임 릴레이(Rust)
├── content-src/  게임 콘텐츠 원본(YAML/PNG)
└── docs/         공통 문서 + 앱별 문서
```

원칙:
- **앱 사이 import 금지.** 공유가 필요하면 `packages/`로 올린다. `packages/ui`는 두 번째 소비자가 생길 때 만든다(미리 만들지 않는다).
- 게임 코드(`apps/phone`, `apps/tv`, `packages/protocol`, `server/`)에 엄빠·포털 로직을 넣지 않는다. 반대도 같다.
- 게임의 콘텐츠 규칙(`content-src`, `build_content.py`)은 게임 전용이다. 엄빠의 시설 데이터는 `apps/cafe/data/`에서 따로 관리한다.

## 4. URL 구조 (확정)

같은 도메인 `kids.aircanvas.kr` 아래 경로로 나눈다.

| 경로 | 내용 | 비고 |
| --- | --- | --- |
| `/` | 포털(메인) | 신규 |
| `/play/` | 게임(지금의 폰 앱) | 지금은 `/`에 있다. 이동 필요 |
| `/tv/` | 게임 TV 앱 | **그대로 유지**(`/tv/?room=` QR 호환) |
| `/ws` | 게임 릴레이 | 그대로 유지 |
| `/manifest.json`, `/artworks/…` | 게임 콘텐츠 서버 | 경로 유지 또는 `/play/` 하위 이동 — 아래 호환 조건 참고 |
| `/cafe/` | 엄빠 | 신규. 현재는 `sk.moru.my` |

경로 방식을 권하는 이유: 인증서·DNS·쿠키가 하나이고 포털에서 하위 서비스로 이동해도 출처가 같다. 대안은 서브도메인(`cafe.kids…`)이며, 엄빠를 독립 배포해야 할 때 고려한다.

### 이동 시 깨지지 않아야 하는 것 (호환 조건)
- 이미 공유된 게임 링크(`/?room=…`, QR)가 계속 열려야 한다. 포털이 쿼리에 `room`/`server`/`content`/`phoneApp`이 있으면 `/play/`로 **쿼리를 보존한 채 전달**한다.
- 폰 앱의 `base`를 `/play/`로 바꾸면 매니페스트·에셋 URL, 서비스 워커/캐시(있다면), `ui-smoke`·`web-debug`의 기준 URL도 같이 바꾼다.
- 엄빠는 `fetch('/api/…')`처럼 **절대경로**를 쓴다(`s-kids/demo/public/index.html`). `/cafe/` 아래로 옮기려면 API 경로를 상대경로 또는 `BASE` 설정으로 바꿔야 한다.
- 엣지 nginx(`/srv/platform/platform-edge-infra/.../conf.d/aircanvas.conf`)는 **이 저장소 밖의 공용 설정**이다. 변경은 사용자 확인 후 `nginx -t` → graceful reload 순서로 하고, 변경 전 파일을 백업한다.

## 5. 이행 순서 (각 단계는 독립 릴리스 가능)

| 단계 | 내용 | 완료 기준 |
| --- | --- | --- |
| **0. 계획 기록** ✅ | 이 문서·규칙 반영 (v0.7.0 직후, 69eb73d) | 문서만, 코드 변화 없음 |
| **1. 포털 신설** ✅ v0.8.0 | `apps/portal` 추가. 게임·엄빠로 가는 카드만 있는 단순 런처. 아직 URL 이동 없음(별도 경로/미리보기로 확인) | `make check`, 포털 `ui-smoke`, 기존 게임 `ui-smoke` 변화 없음 |
| **2. 엄빠 이관** ✅ v0.8.0 | `git subtree add --prefix=apps/cafe`로 **s-kids 이력 보존** 병합. 기존 `sk.moru.my` 컨테이너는 그대로 둔다 | 이관된 코드로 `docker compose`가 기존과 같은 응답, `sk.moru.my` 무중단 |
| **3. 경로 전환** ✅ v0.8.0 | 폰 앱 `base=/play/`, 포털을 `/`, 엄빠를 `/cafe/`로 엣지에 연결. 레거시 쿼리 전달 포함 | 공개 URL에서 기존 QR/링크·TV 연결·엄빠 API 모두 동작, `make ui-smoke`·`make web-debug` 통과 |
| **4. 공용 UI 추출** ✅ v0.8.0 | 포털·엄빠에서 실제로 겹치는 것만 `packages/ui`로 | 두 앱이 같은 토큰을 쓰고 시각 회귀 없음 |
| **5. 정리** ⏳ | `sk.moru.my`를 `/cafe/`로 301, 구 s-kids 저장소는 아카이브 표시(삭제하지 않는다) | 리다이렉트 확인 |

단계 2~3의 외부 영향(엣지 설정·DNS·원격 저장소·구 저장소 아카이브)은 각각 **실행 직전에 사용자에게 확인**한다.

## 6. 결정 기록과 남은 미결정

결정됨(2026-10-21): URL은 경로 방식, 게임은 `/play/`, 버전·태그는 저장소 전체 semver 하나, UI는 게임의 디자인 콘셉트(숲 녹색·살구색)를 유지하고 엄빠를 그 토큰으로 재단장.

남은 것:
1. 저장소 이름(`aircanvas-kids`)을 바꿀지. 원격 저장소 이름 변경은 외부 영향이 있어 마지막에 결정한다.
2. 단계 5: `sk.moru.my`를 `/cafe/`로 301 전환하고 구 `s-kids` 저장소를 아카이브할지(삭제하지 않는다). 사용자 확인 후 실행한다.
3. 엄빠의 예약 현황은 **시뮬레이션**이다. 실제 수집·재표시는 운영기관 허용 확인 전에는 하지 않는다(`apps/cafe/docs/LEGAL_AND_ROBOTS.md`). 실데이터로 바꾸는 시점에 포털 문구의 "데모 데이터" 표기를 함께 정리한다.
4. 포털에 아직 서비스가 둘뿐이다. 새 서비스가 늘어 카드 수가 많아지면 포털 레이아웃(그룹·검색)을 다시 본다.

## 8. 서비스 추가 방법 (포털 카드)

1. `apps/<이름>/`에 앱을 둔다(정적 앱이면 Vite 앱, 서버가 필요하면 `apps/cafe`처럼 컨테이너). 앱 사이 import는 금지, 공유는 `packages/`.
2. 공개 경로는 `/<이름>/`로 정하고, 엣지 nginx에 `location /<이름>/`을 추가한다(**저장소 밖 공용 설정 — 사용자 확인 후** `nginx -t` → graceful reload).
3. 정적 앱을 `site/` 아래로 내려야 하면 `tools/build-site.sh`에 한 줄을 추가한다. 서버 앱은 `docker-compose.yml`과 헬스체크를 둔다.
4. `apps/portal/services.json`의 `services`에 항목을 추가한다. 포털 코드는 고치지 않는다.

| 필드 | 설명 |
| --- | --- |
| `id` | 영문 소문자 식별자. 카드의 `data-testid`는 `service-<id>` |
| `audience` | 누가 쓰는지(예: `아이와 함께`, `엄빠용`). 카드 위쪽 작은 글씨 |
| `title` / `summary` | 카드 제목·한두 문장 설명(사용자 눈높이, 시스템 용어 금지) |
| `cta` | 버튼 문구. 동사로 끝낸다(예: `놀러 가기`, `일정 보기`) |
| `href` | 이동 경로(`/<이름>/`) |
| `tone` | `forest`(진한 카드, 아이용 기본) 또는 `cream`(밝은 카드, 보호자용 기본) |
| `emoji` | 카드 장식. **라이선스가 불분명한 일러스트는 쓰지 않는다**(공룡 5종 일러스트는 출처 확인 전이라 포털에 쓰지 않았다) |
| `tag` | (선택) 작은 배지. 데모·베타 등 상태 표기 |
| `status` | (선택) `soon`이면 링크 없이 "곧 열려요"로 표시 |

5. `tools/site-smoke.py`의 카드 개수 기대값과 새 서비스 연결 확인을 갱신하고 `make site-smoke`를 통과시킨다.
6. 새 서비스의 문서(`apps/<이름>/README.md` 또는 `docs/`)와 이 문서를 갱신한다. 디자인은 `packages/ui/tokens.css`의 토큰을 쓴다.
