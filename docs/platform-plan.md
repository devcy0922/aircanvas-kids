# 플랫폼 확장 계획 — 포털 + 게임 + 엄빠(서울형 키즈카페)

> **상태: 계획(미구현).** 2026-10-21 사용자 방향 결정을 기록한다. 이 문서의 구조는 아직 코드에 반영되지 않았으며,
> 현재 동작은 `README.md`·`docs/architecture.md`가 기준이다. 구현이 끝난 항목만 해당 문서로 옮기고 여기서는 "완료"로 표시한다.

## 1. 결정된 것 (사용자 지시)

- `kids`는 앞으로 **어린이·육아 관련 여러 콘텐츠를 담는 제품**이다. 지금까지 만든 공중 색칠 게임은 그중 **게임** 기능이다.
- **메인 페이지를 별도로 새로 만들고**, 게임은 그 아래 하위 페이지(기능) 하나로 둔다.
- 이전에 만든 **서울형 키즈카페 "엄빠"**(`/srv/products/s-kids`)를 새 하위 페이지로 붙인다.
- 저장소는 **모노레포**로 가는 방향을 검토한다(권고는 §2).

## 2. 모노레포 권고

**권고: 예. 다만 한 번에 합치지 않고 §5의 순서로 단계적으로 합친다.**

| 관점 | 판단 |
| --- | --- |
| 이미 npm workspaces(`apps/*`, `packages/*`)다 | 새 앱은 `apps/` 아래에 추가만 하면 된다. 구조 전환 비용이 작다. |
| 메인 페이지가 두 하위 서비스를 연결한다 | 링크·공용 디자인 토큰·공통 셸을 한 저장소에서 같이 바꿔야 어긋나지 않는다. |
| 혼자(사람+에이전트) 운영한다 | 저장소·체크리스트·배포 절차를 하나로 유지하는 쪽이 부담이 적다. |
| 스택이 다르다 | 게임은 Vite/React + Rust 릴레이, 엄빠는 의존성 없는 Node 서버 + 단일 HTML이다. **코드를 섞지 않고 앱 단위로 격리**하면 문제없다. |
| 법적·운영 성격이 다르다 | 엄빠는 외부 공공데이터·예약 사이트 호출 정책(`s-kids/docs/LEGAL_AND_ROBOTS.md`)이 있다. 문서·검증을 `apps/cafe` 안에 두고 게임 규칙과 섞지 않는다. |

**합치지 않는 편이 나은 경우**(현재는 해당 없음): 팀이 분리되거나, 엄빠가 별도 도메인·별도 일정으로 독립 출시될 때.

## 3. 목표 구조

```text
aircanvas-kids/                 (저장소 이름은 유지. 변경은 별도 결정)
├── apps/
│   ├── portal/   신규  kids 메인(런처). 정적 SPA, 서버 없음
│   ├── phone/    기존  게임: 폰 앱 (이름·경로는 당분간 유지)
│   ├── tv/       기존  게임: TV 앱
│   └── cafe/     이관  엄빠: s-kids의 demo/ (Node 서버 + 정적 파일 + data)
├── packages/
│   ├── protocol/ tv-art/   게임 전용 — 다른 앱이 import하지 않는다
│   └── ui/       신규(필요해지면)  포털·엄빠가 함께 쓰는 디자인 토큰·셸
├── server/       게임 릴레이(Rust)
├── content-src/  게임 콘텐츠 원본(YAML/PNG)
└── docs/         공통 문서 + 앱별 문서
```

원칙:
- **앱 사이 import 금지.** 공유가 필요하면 `packages/`로 올린다. `packages/ui`는 두 번째 소비자가 생길 때 만든다(미리 만들지 않는다).
- 게임 코드(`apps/phone`, `apps/tv`, `packages/protocol`, `server/`)에 엄빠·포털 로직을 넣지 않는다. 반대도 같다.
- 게임의 콘텐츠 규칙(`content-src`, `build_content.py`)은 게임 전용이다. 엄빠의 시설 데이터는 `apps/cafe/data/`에서 따로 관리한다.

## 4. URL 구조 (제안 — 사용자 확인 전)

같은 도메인 `kids.aircanvas.kr` 아래 경로로 나눈다.

| 경로 | 내용 | 비고 |
| --- | --- | --- |
| `/` | 포털(메인) | 신규 |
| `/play/` | 게임(지금의 폰 앱) | 지금은 `/`에 있다. 이동 필요 |
| `/tv/` | 게임 TV 앱 | **그대로 유지**(`/tv/?room=` QR 호환) |
| `/ws` | 게임 릴레이 | 그대로 유지 |
| `/manifest.json`, `/artworks/…` | 게임 콘텐츠 서버 | 경로 유지 또는 `/play/` 하위 이동 — 아래 호환 조건 참고 |
| `/cafe/` | 엄빠 | 신규. 현재는 `sk.moru.my` |

경로 방식을 권하는 이유: 인증서·DNS·쿠키가 하나이고 포털에서 하위 서비스로 이동해도 출처가 같다. 대안은 서브도메인(`cafe.kids…`)이며, 엄빠를 독립 배포해야 할 때 고려한다.

### 이동 시 깨지지 않아야 하는 것 (호환 조건)
- 이미 공유된 게임 링크(`/?room=…`, QR)가 계속 열려야 한다. 포털이 쿼리에 `room`/`server`/`content`/`phoneApp`이 있으면 `/play/`로 **쿼리를 보존한 채 전달**한다.
- 폰 앱의 `base`를 `/play/`로 바꾸면 매니페스트·에셋 URL, 서비스 워커/캐시(있다면), `ui-smoke`·`web-debug`의 기준 URL도 같이 바꾼다.
- 엄빠는 `fetch('/api/…')`처럼 **절대경로**를 쓴다(`s-kids/demo/public/index.html`). `/cafe/` 아래로 옮기려면 API 경로를 상대경로 또는 `BASE` 설정으로 바꿔야 한다.
- 엣지 nginx(`/srv/platform/platform-edge-infra/.../conf.d/aircanvas.conf`)는 **이 저장소 밖의 공용 설정**이다. 변경은 사용자 확인 후 `nginx -t` → graceful reload 순서로 하고, 변경 전 파일을 백업한다.

## 5. 이행 순서 (각 단계는 독립 릴리스 가능)

| 단계 | 내용 | 완료 기준 |
| --- | --- | --- |
| **0. 계획 기록** | 이 문서·규칙 반영 (지금 단계) | 문서만, 코드 변화 없음 |
| **1. 포털 신설** | `apps/portal` 추가. 게임·엄빠로 가는 카드만 있는 단순 런처. 아직 URL 이동 없음(별도 경로/미리보기로 확인) | `make check`, 포털 `ui-smoke`, 기존 게임 `ui-smoke` 변화 없음 |
| **2. 엄빠 이관** | `git subtree add --prefix=apps/cafe`로 **s-kids 이력 보존** 병합. 기존 `sk.moru.my` 컨테이너는 그대로 둔다 | 이관된 코드로 `docker compose`가 기존과 같은 응답, `sk.moru.my` 무중단 |
| **3. 경로 전환** | 폰 앱 `base=/play/`, 포털을 `/`, 엄빠를 `/cafe/`로 엣지에 연결. 레거시 쿼리 전달 포함 | 공개 URL에서 기존 QR/링크·TV 연결·엄빠 API 모두 동작, `make ui-smoke`·`make web-debug` 통과 |
| **4. 공용 UI 추출** | 포털·엄빠에서 실제로 겹치는 것만 `packages/ui`로 | 두 앱이 같은 토큰을 쓰고 시각 회귀 없음 |
| **5. 정리** | `sk.moru.my`를 `/cafe/`로 301, 구 s-kids 저장소는 아카이브 표시(삭제하지 않는다) | 리다이렉트 확인 |

단계 2~3의 외부 영향(엣지 설정·DNS·원격 저장소·구 저장소 아카이브)은 각각 **실행 직전에 사용자에게 확인**한다.

## 6. 미결정 (사용자 결정 필요)

1. URL을 경로 방식(§4)으로 갈지, 서브도메인으로 갈지.
2. 버전·태그 정책. **권고: 당분간 저장소 전체가 하나의 semver를 쓴다**(포털·게임·엄빠 중 무엇이 바뀌어도 같은 `vX.Y.Z` 흐름). 앱별 독립 배포가 필요해지면 `game-v…`/`cafe-v…` 접두 태그로 전환한다. 확정되면 `agents/rules.md` §7을 앱 범위에 맞게 고친다.
3. 엄빠를 `/cafe/` 등 어떤 이름으로 부를지, 포털의 브랜드·이름("kids")과 디자인 방향.
4. 저장소 이름(`aircanvas-kids`)을 바꿀지. 원격 저장소 이름 변경은 외부 영향이 있어 마지막에 결정한다.
5. 엄빠의 예약 현황 수집·재표시는 **운영기관 허용 확인 전**이다(`s-kids/docs/LEGAL_AND_ROBOTS.md`). 공개 포털에 노출하기 전에 이 상태를 포털 문구에 어떻게 표시할지 정한다.

## 7. 위험과 대응

| 위험 | 대응 |
| --- | --- |
| 폰 앱 경로 이동으로 기존 링크·QR이 깨진다 | §4 호환 조건 + 공개 URL에서 쿼리 보존 확인 |
| 한 저장소의 체크리스트가 서로 다른 앱에 안 맞는다 | 단계 3 이후 `rules.md` §7을 앱 범위별로 정리(게임 전용 항목: Rust·`web-debug`·콘텐츠 빌드) |
| 엄빠 이관 중 운영 중인 `sk.moru.my`가 끊긴다 | 단계 2에서는 기존 컨테이너를 유지하고 새 위치에서 동일 응답을 확인한 뒤 전환 |
| 공용 UI를 성급히 추출해 결합이 커진다 | 두 번째 실제 소비자가 있을 때만 `packages/ui` 생성 |
